# План Rust CLI для Rozm: текст → WAV

Дополнение выполнено по запросу Node.js-библиотеки: `nodejs/` предоставляет
`createAudioStream(text, options): Readable`, а CLI поддерживает `--stdin`
и `--output -`. Текст идёт по UTF-8 stdin, WAV — по бинарному stdout,
без аудиофайлов. Каждый вызов владеет отдельным Rust-процессом; ошибки,
backpressure, AbortSignal и destroy обрабатываются библиотекой. Синтез
собирает PCM до первого WAV-байта. MP3 остаётся отложенным. Готовый npm-архив
включает оба целевых бинарника и данные; Python не нужен.

## Согласованные требования

Нативное консольное приложение на Rust без GUI, интерактивного входа пользователя и аудиоустройства. Основная платформа — Linux x86_64, Ubuntu 24.04 (`x86_64-unknown-linux-gnu`); дополнительная — Win32 x86 (`i686-pc-windows-msvc`). Win32 означает 32-битный Windows EXE, а не поддержку исторических Windows XP/7.

Один вызов создаёт один WAV. MP3-кодирование отложено до явной просьбы: не подключать и не запускать LAME, не реализовывать MP3-exporter. В коде оставить общий интерфейс экспортирования для будущих форматов. Сейчас допустим только WAV; `.mp3` и другие расширения отклонять с понятной ошибкой.

```sh
# Ubuntu: результат в ./out.wav
./rozm-cli --text 'Привіт, світе!'
./rozm-cli --text 'Привіт, світе!' --output ./result.wav --voice 2 --speed 4
```

```powershell
# Win32: результат в текущей директории
.\rozm-cli.exe --text 'Привіт, світе!'
```

Интерфейс реализован. Инструкции запуска и сборки — в README.md.

- `--text`: обязательный текст одним аргументом; внутренние кавычки и реальные переводы строк допустимы.
- `--output`: необязательный путь, по умолчанию `./out.wav` относительно текущей рабочей директории. Существующий файл перезаписывается без подтверждения.
- `--voice`: 1–3, по умолчанию 1 (Анатоль); остальные голоса — Стьопа и Руся.
- `--speed`: целое 1–9, по умолчанию 5.

Ошибки аргументов, текста, формата, ресурсов, синтеза и записи возвращают ненулевой код и сообщение в stderr. Пакетное разбиение и дополнительные способы ввода текста не входят в первую версию.

## Как устроен оригинал

`orig/Rozm.exe` — нативный Delphi/VCL Windows x86 PE32. Исходников нет. `orig/Rozm.txt` содержит ссылки из дизассемблера. Статическое исследование дополнено исполнением исходных процедур текста/синтеза в исследовательском эмуляторе; GUI-экспорт отдельно не проверен. Ориентиры сохранены в `docs/original-engine.md`.

WAV-handler получает текст из RichEdit, включает запись и синхронно вызывает обработку `0x4678B4`, затем ядро `0x466E7C`. В файловой ветке `0x46756A…0x46768A` блоки PCM записываются без `waveOut`; обновляются размеры RIFF/data. Шаблон `wavhead.wav` задаёт PCM mono, 11025 Гц, 8 бит. Defaults подтверждены: голос 1, скорость 5.

Пользовательского CLI не обнаружено. Подготовка данных смешана с VCL и аудиоустройством; директивы смены голоса также обращаются к форме. MP3 оригинал получает через внешний LAME — это факт исследования, а не этап текущего плана.

## Способ реализации

Прежний подход с новым входом в изменённой копии PE заменить восстановлением файлового пути синтеза на Rust. Windows EXE нельзя напрямую использовать в нативном Linux x86_64 процессе. `Rozm.exe` остаётся источником алгоритмов и Windows-эталоном; обязательного Wine, x86-эмуляции и C/C++-прослойки в основной архитектуре нет.

Последовательно восстановить форматы данных, преобразования текста, фонетику и построение PCM; сохранить установленные особенности произношения, голоса и скорости. Форматы читать явными little-endian полями фиксированной ширины. Не переносить адреса процесса, указатели Delphi, AnsiString ABI и размеры `usize` в формат файлов; это важно при переходе с x86 на x86_64.

Допустимо повторно использовать бинарные данные `BSNbn`, `skfs/{skf,wif,wlf}`, `snf{1,2,3}/{ip2f,lp2f,Sd2f}`, при необходимости `wavhead.wav` и другие подтверждённые ресурсы. До подключения установить назначение, размеры и проверки целостности каждого файла. Соблюдать регистр имён на Linux, особенно `Sd2f`. Исходный комплект не изменять.

Установленный комплект содержит `data/` рядом с бинарником. При разработке допускается `ROZM_DATA_DIR`, указывающий на локальный `orig/`. Поиск ресурсов не должен зависеть от текущей директории. Использовать переносимые filesystem API Rust; ожидаемую кодировку Windows-1251 проверить по таблицам и алгоритмам оригинала. Непредставимые символы не заменять молча на `?`.

```text
Cargo.toml / Cargo.lock   пакет и фиксированные зависимости
src/main.rs              вход CLI и код завершения
src/cli.rs               аргументы и настройки
src/text/                валидация и преобразования текста
src/resources/           загрузка бинарных данных
src/engine/              переносимый синтез текста в PCM
src/export/mod.rs        общий интерфейс exporter
src/export/wav.rs        WAV-exporter
tests/fixtures/          проблемные тексты и будущие эталоны
docs/                   ориентиры и описание форматов
data/                   место для бинарных зависимостей
orig/                   исходный комплект вне Git
```

Конвейер: аргументы → валидация → ресурсы → PCM → exporter → файл. `AudioExporter` получает PCM и `Write`; существует только `ExportFormat::Wav`. Реализован WAV-exporter; MP3-заглушек и LAME нет.

## Выходной файл

Создавать новый WAV вместо append. В реализации записывать временный файл в директории назначения, завершать WAV и заменять пользовательский файл без подтверждения. Очищать временный файл при ошибке. Проверить замену на Linux и Windows: rename/replace и поведение открытого файла отличаются. Если ОС не разрешает замену, вернуть ошибку. Ошибка до завершения синтеза не должна уничтожать прежний результат.

## Проверки проблемного --text

Читать argv через `std::env::args_os`, без паники при непредставимом Unicode. Преобразование текста проверять явно, пути хранить в `PathBuf`. Текст не собирать в shell-команду и не выполнять. Shell удаляет внешние кавычки до передачи argv, поэтому отдельно проверить доставку аргументов и обработку полученного текста.

Нужны интеграционные проверки реального процесса с прямой передачей argv и дополнительные проверки через Bash Ubuntu 24.04 / PowerShell Windows:

- Одинарные и двойные кавычки, украинские апострофы, обратный слеш и их сочетания.
- Реальные LF, CRLF, CR: корректная нормализация, без обрезания оставшегося текста.
- Отличать перевод строки от двух символов `\` и `n`; не преобразовывать escape-последовательности автоматически.
- Начальный дефис (`--text=-приклад`) и похожие на опции фрагменты внутри текста.
- `$`, обратные кавычки, `;`, `&`, `|`, скобки: при прямой передаче это только текст.
- Украинские буквы, типографские кавычки, emoji и комбинируемые знаки: синтез либо предсказуемая ошибка, без падения и молчаливой порчи.
- Пустой/пробельный текст, длинный аргумент, некорректный Unicode argv: контролируемая ошибка, без panic/segfault/зависания.

NUL нельзя передать внутри обычного аргумента процесса. В первоначальной версии тестировался только CLI-процесс. В последующем Node.js-расширении пользователь согласовал публичный Node.js API и CLI; NUL проверяется через stdin и Node.js. Установлены пределы: 32768 UTF-8 байт текста, 32 MiB на ресурс, 64 MiB PCM; каждый тестовый процесс имеет дедлайн 30 секунд. Начальная подборка случаев находится в `tests/fixtures/text-cases.json`, исполняемые проверки — в `tests/cli.rs` и `nodejs/test/`.

## Этапы и приёмка

1. **Каркас и форматы.** Настроить Rust-модули, интерфейс экспорта и тестовые данные. Зафиксировать бинарники и карту алгоритмов; восстановить загрузку данных с проверками границ.
2. **Минимальный нативный синтез на Ubuntu 24.04.** Перенести путь текст → PCM → WAV без оригинального EXE и аудиоустройства. Проверить корректный непустой WAV; сравнить PCM с экспортом оригинала при одинаковых параметрах. Уточнять неизвестные алгоритмы до расширения покрытия.
3. **Полный WAV CLI.** Реализовать четыре аргумента, необязательный output, перезапись, все голоса/скорости и весь текст. Проверить проблемные символы и исходные директивы без обращения к GUI.
4. **Win32 и общий набор проверок.** Собрать и выполнить тесты на Windows x86; проверить эквивалентность PCM между платформами. Проверить другую рабочую директорию, пробелы/кириллицу в путях, ошибки ресурсов/записи, повторные вызовы, работу без рабочего стола и аудиоустройства.

Приёмка: нативный Linux x86_64 и Win32 результат; один WAV на вызов; `./out.wav` по умолчанию; перезапись без вопроса; отсутствие сбоев на перечисленных вводах. MP3 может стать отдельным этапом только после явной просьбы.

## Результат реализации и границы совместимости

Реализованы нативный Rust-конвейер, чтение словарей и банков, ударение/фонетика, числа, символы, сокращения, Latin fallback, все три голоса, скорость Анатоля, WAV и CLI. Структура каталогов и gitignore настроены; упаковка копирует необходимые данные, не меняя оригинал. Проверки проходят через согласованную границу CLI-процесса. Сборки и результаты целевых платформ фиксируются в `docs/validation.md`.

Эталоны получены из оригинальных машинных процедур, независимо от Rust-кода; побайтовое совпадение доказано для тестового корпуса. Полная эквивалентность произвольного текста и GUI-экспорт этим не доказываются. В исходном комплекте отсутствует EUtDic.txt, поэтому переносится Latin fallback. Сохраняются особенности оригинала: скорость голосов 2/3 не меняется, нормализация пропускает ґ/Ґ. Точность неизвестных слов зависит от исходного словаря. Активация и GUI оригинала не являются частью нового CLI и не изменяются.

Официальные ориентиры Rust: [платформы](https://doc.rust-lang.org/rustc/platform-support.html), [args_os](https://doc.rust-lang.org/std/env/fn.args_os.html).
